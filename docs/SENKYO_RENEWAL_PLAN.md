# senkyo 기능·디자인·UX 통합 개편안

작성일: 2026-10-06
개정: 겨울·크리스마스 디자인 및 화면별 UX 명세 추가
대상: ahapwhs0414/senkyo 기본 브랜치(main)
상태: 구현 전 제안서. 저장소 코드·문서를 검토했으며 운영 Vercel 환경변수, Google Cloud 설정, 실제 사용자 DB 및 브라우저 오류는 확인하지 않았다. 따라서 운영 장애의 최종 원인을 확정하거나 수정 완료로 판단하지 않는다.

## 1. 개편 목표와 관리 경계

사전에 확정한 여행 계획을 편하게 조회하고, 현장에서 예약자료와 준비 상태를 관리하는 서비스로 개편한다.

- 계획서에서 관리: 날짜, 시간, 일정 순서, 장소, 이동 경로, 식사별 복수 식당과 표시 순서, 지도 링크.
- 사이트에서 관리: 예약번호·좌석·확인 메모·첨부파일, 일정별 준비물과 체크리스트 작성 및 수정, 완료 체크.
- 삭제: 지출 입력·정산, 일정 추가/편집/삭제/순서 변경, 장소 검색·등록·수정, 후보 식당 등록·선택·변경 UI.
- 유지: 두 계정 로그인, 예약과 첨부 보안, 오늘·일정 조회, 지도 및 길찾기, 준비 상태 동기화.
- 삭제 요청에 포함되지 않은 쇼핑·긴급정보는 유지한다. 예정 교통요금 등 계획서의 참고 금액은 읽기 전용으로 유지하되 지출·분담·정산 집계는 제거한다.

## 2. Google Maps 문제: 확인된 사실과 진단

### 2.1 코드에서 확인한 사실

| 확인 위치 | 사실 | 영향 |
|---|---|---|
| scripts/generate-seed.mjs | 초기 장소의 google_place_id가 null | 장소 이름이 있어도 Google 지점이 연결된 것은 아니다 |
| src/components/travel-map.tsx | Place ID별 /api/places 상세조회 결과의 location으로 마커 생성 | 지도 스크립트가 정상이어도 ID 또는 Places 응답이 없으면 마커가 없다 |
| src/app/api/places/route.ts | GOOGLE_MAPS_SERVER_API_KEY가 없으면 503 응답 | 브라우저 지도 키만 넣어서는 Places 조회가 동작하지 않는다 |
| src/components/travel-map.tsx | NEXT_PUBLIC_GOOGLE_MAPS_API_KEY 사용 | 서버 Places 키만 넣어서는 내장 지도가 동작하지 않는다 |
| src/lib/domain.ts | mapsUrl은 Google Maps URL을 생성 | 외부 지도 링크는 내부 API 성공 여부와 분리할 수 있다 |
| src/components/travel-map.tsx | script.onload 후 초기화하며 인증 실패 전용 처리가 명시돼 있지 않음 | 스크립트 다운로드 성공과 API 인증 성공을 구별하는 오류 처리가 필요하다 |

운영 DB에 사용자가 지점을 연결했는지는 미확인이다. Seed의 null 값만으로 운영 데이터까지 모두 비어 있다고 단정하지 않는다.

### 2.2 장애 진단 순서

1. 실패 기능을 구분한다: 지도 배경 / 지도 마커 / 장소 상세·사진 / Google Maps 외부 링크.
2. 배포된 커밋과 Vercel Production 환경변수 이름·적용 대상을 확인한다. 값 자체를 로그나 문서에 남기지 않는다. NEXT_PUBLIC 값 변경 후에는 새 빌드와 재배포가 필요하다.
3. 브라우저 콘솔에서 Maps 오류 코드를 확인한다. RefererNotAllowedMapError는 허용 도메인, ApiNotActivatedMapError는 활성 API, BillingNotEnabled 계열은 결제 연결 상태를 확인한다.
4. 로그인한 상태에서 /api/places 응답과 서버 로그의 HTTP 상태·오류 코드를 확인한다. 503은 키 미설정, Google의 제한·권한 오류는 키/API 제한을 확인한다. 인증 실패와 Google 실패를 구분한다.
5. 브라우저 키는 Maps JavaScript API 및 실제 서비스 웹사이트 referrer로 제한한다. 서버 Places 키에 브라우저용 HTTP referrer 제한을 적용하지 않는다. 서버 키는 Places API (New)와 실제 서버 실행 환경에 맞는 제한을 적용한다. 고정 송신 IP가 없는 환경에 임의 IP를 등록하지 않는다.
6. 실제 DB의 일정↔장소 연결, Place ID, 상세 응답의 좌표 유무를 확인한다.
7. 장소명은 같아도 다른 지점일 수 있으므로 계획서에 담을 실제 지점과 링크를 대조한다.

### 2.3 개편 후 권장 구조

기본 지도 기능은 **계획서에 검증한 Google Maps 링크를 넣고 일정 카드에서 바로 여는 방식**으로 한다. Google Maps URLs는 API 키 없이 사용할 수 있다.

- 식당마다 ‘지도 보기’와 필요시 ‘길찾기’를 제공한다.
- 검증한 Google Maps 공유 링크가 있으면 그대로 사용한다. 생성형 검색 URL은 api=1과 인코딩한 장소명·주소를 사용하고, 확인된 Place ID가 있으면 query_place_id를 함께 제공한다.
- Place ID, 정확한 지점 URL 또는 좌표를 추측해서 만들지 않는다. 미확정 지점은 계획서에서 확인 필요로 표시한다.
- 외부 링크 버튼을 Places 상세·사진 로딩 성공 조건에 묶지 않는다.
- 날짜별 내장 지도는 유지하되 부가 기능으로 취급한다. API 오류가 나면 같은 화면에 일정순 장소 목록과 검증된 지도 링크를 보여준다.
- 현행 내장 지도는 Places API에 의존하므로 ‘장소 검색 UI 삭제’를 이유로 /api/places 전체를 바로 삭제하지 않는다. 검색·사진·상세 중 실제 사용 중인 기능을 분리한 후 필요한 조회만 남긴다.
- 지도 조회 실패, 지점 미연결, 해당 날짜 장소 없음, 일부 마커만 성공한 상태를 구분한다.
- 고정 열차·항공·셔틀 시간은 지도 추천 시간으로 변경하지 않는다.

## 3. 기능별 수정 명세

### 3.1 지출 및 정산 삭제

지출 등록·수정·삭제, 결제자/분담 방식, 정산 합계, 오늘 지출 요약, 관련 메뉴와 API 호출을 제거한다. 클라이언트 데이터 조회에서도 expenses/expense_splits를 제외한다.

UI만 숨기지 말고 일반 사용자 요청으로 해당 데이터를 변경할 수 없도록 API 허용 목록과 DB 권한을 함께 정리한다. 기존 데이터는 우선 보존하고, 조회·참조·백업 확인 후 별도의 정리 migration에서 테이블 제거 여부를 결정한다.

### 3.2 일정·장소 편집 제거

일정 제목·시간·날짜·순서·장소·이동 경로를 읽기 전용으로 만든다. 일정 추가, 드래그 정렬, 편집 폼, 장소 검색/연결 버튼을 제거한다.

예약정보와 준비물 편집은 별도 액션으로 남긴다. 일반 두 계정은 계획 데이터에 대해 SELECT만 가능하도록 하되, 예약/준비물/체크 상태의 기존 편집 권한은 유지한다. 계획 반영은 개발 배포 절차로 수행한다.

일정 완료/건너뜀 표시를 유지할 경우 계획 본문과 분리한 진행 상태만 수정하도록 한다. 일정 변경 API를 그대로 허용하는 우회 방식은 사용하지 않는다.

### 3.3 장소·후보 식당 기능 제거 및 식사 카드 통합

장소 탭과 후보 식당 관리 화면을 없앤다. 다만 지도·일정·식사에서 필요한 장소 데이터와 참조 관계는 유지한다.

식사 일정의 상세 화면에 계획서에서 정한 여러 식당을 고정 목록으로 표시한다.

- 식당명과 정확한 지점명
- 음식 종류 및 계획서에 기재한 짧은 설명
- 계획서 표시 순서
- 각 식당의 Google Maps 링크
- 예약 관련 메모가 있으면 예약정보 연결

사용자는 목록을 보고 현장에서 방문할 식당을 결정할 수 있지만, 웹사이트에는 후보 추가·삭제·교체·순위 변경·선택 저장 기능을 두지 않는다. 실시간 평점·사진·영업시간은 핵심 요구사항에서 제외한다. 계획서에 적는 정보는 확인일을 명시한다.

기존 meal_candidates가 유일한 식사 연결 원본이라면 고정 schedule_places 관계 또는 이에 준하는 고정 연결 구조로 이관한 뒤 사용을 중단한다. 장소 테이블을 먼저 삭제해 예약·이동·지도 연결을 끊지 않는다.

### 3.4 이동 일정에서 예약 텍스트·파일 관리

이동 카드의 ‘예약자료’ 버튼으로 같은 일정 안에서 예약자료를 확인하고 추가한다.

- 텍스트만, 파일만, 텍스트와 파일 모두 저장 가능
- 예약번호, 예약자, 편명/열차명, 좌석, 탑승 위치, 안내 메모
- PDF 및 이미지 보기·다운로드
- 여러 첨부 지원, 파일별 제목과 설명
- 저장·업로드 실패 및 재시도 상태 표시

기존 reservations → reservation_schedule_items → reservation_attachments 구조를 우선 재사용한다. 일정에 자료를 추가할 때 연결된 예약을 선택하거나 새 자료용 예약을 만들고 일정 연결을 함께 처리한다. 하나의 일정에 여러 예약이 연결돼도 모두 보이며, 하나의 예약을 여러 일정에서 참조할 수 있어야 한다.

이미 텍스트 첨부, private Storage, 10MB 제한, PDF/PNG/JPEG/WEBP 검증, 60초 signed URL 구조가 문서화돼 있다. 이를 이동 상세로 연결하고 실제 기존 migration 적용 여부를 확인한다. 텍스트는 HTML로 실행하지 않는다. 업로드 후 DB 연결이 실패하면 파일 정리 또는 재시도 가능한 상태를 제공한다.

사이트 안에 저장한 자료만으로 예약정보를 확인할 수 있도록 만들되, 실제 탑승·입장에는 사업자의 원본 앱이나 갱신되는 QR이 필요할 수 있다. 이를 임의로 정적 첨부로 대체했다고 표시하지 않는다.

현재 오프라인은 같은 탭에서 조회한 정보의 제한적 스냅샷이며 첨부파일은 캐시하지 않는다. 이번 기본 범위는 온라인 조회와 사전 다운로드다. 완전한 오프라인 첨부 보관은 별도 기능으로 분리한다.

### 3.5 일정별 준비물·체크리스트 및 여행 전 할 일

준비물은 물건/자료, 체크리스트는 행동으로 분리한다. 예: ‘여권’은 준비물, ‘항공편 체크인’은 할 일이다.

기존 packing_items/checklist_items의 schedule_item_id를 활용하여 일정 상세에서 항목 추가·수정·삭제·완료 체크를 지원한다. 일정 본문이 읽기 전용이어도 이 항목들은 수정할 수 있다.

| 범위 | 표시 위치 | 완료 규칙 |
|---|---|---|
| 여행 전 할 일 | 출발 전 준비 목록 | 여행 전체에서 한 번 완료 |
| 공통 준비물 | 적용되는 여행 날짜의 오늘 및 준비 화면 | 매일 휴대 여부를 체크하려면 날짜별 상태 |
| 일정별 준비물 | 일정 상세 및 해당 날짜 전체보기 | 일정 또는 연결된 날짜 기준 상태 |
| 일정별 할 일 | 일정 상세 및 해당 날짜 전체보기 | 원칙적으로 해당 항목 한 번 완료 |
| 기존 날짜별 항목 | 해당 날짜 전체보기 | 일정 매핑 전까지 보존 |

여행 전 할 일은 PRE_TRIP 같은 명시적 구분을 추가한다. 단순히 date=null로만 표현하면 현재 inScope 함수가 모든 여행 날짜에 포함하므로 반복 노출 문제가 생긴다. 출발 전 할 일의 마감일은 표시와 정렬에 활용하고, 여행 중 미완료가 있으면 ‘출발 전 미완료’로 별도 표시한다.

‘짐 싸기 완료’와 ‘오늘 휴대함’을 같은 checked 값으로 처리하지 않는다. 반복 준비물이 필요하면 항목 정의와 일별 체크 상태를 분리하고 (항목 ID, 날짜, 담당자)에 유일성을 둔다. SHARED는 공동 상태, 개인 담당 항목은 담당자별 상태로 정의한다.

동일 물건을 여러 일정에서 필요로 하면 공통 항목 ID와 연결 관계로 묶는다. 이름 문자열이 같다는 이유만으로 합치지 않는다. 두 사람의 여권이나 서로 다른 예약 티켓은 별도 항목으로 유지한다.

### 3.6 오늘 전체보기 팝업

현재 planner.tsx의 ‘체크리스트 전체’와 ‘준비물 전체’는 changeView로 화면을 전환한다. 이를 오늘 화면의 모달/모바일 바텀시트 상태로 변경한다.

- ‘준비물 전체’: 해당 날짜 팝업을 열고 준비물 영역 활성화
- ‘체크리스트 전체’: 같은 팝업을 열고 할 일 영역 활성화
- 팝업 안에서 두 영역을 전환 가능
- 공통 항목 + 해당 날짜 모든 일정의 항목 + 기존 날짜 전용 항목을 합산
- 완료 항목 포함 전체보기, 미완료 필터, 완료 수/전체 수 표시
- 공통 → 시간순 일정 그룹으로 정렬하고 항목별 관련 일정 표시
- 체크 즉시 오늘 카드·일정 상세·준비 화면에 동일 상태 반영
- 저장 실패 시 원상 복구와 오류 안내; 다른 계정의 변경 동기화
- 닫으면 날짜·탭·스크롤 위치 유지
- 키보드 포커스 고정/복귀, ESC 닫기, 배경 스크롤 잠금, 320px 화면 지원

오늘의 날짜 판정은 기존 Asia/Tokyo를 유지한다. 여행 전에는 ‘출발 전 준비’와 1일차 미리보기를 구분하고, 선택 날짜가 오늘이 아니면 ‘오늘’로 오인하지 않도록 표시한다.

## 4. 화면 구성 제안

하단 탭은 ‘오늘 / 일정 / 지도 / 준비 / 더보기’를 권장한다. 삭제되는 장소 탭을 준비 탭으로 바꾼다.

- 오늘: 지금/다음 일정, 이동 예약자료, 당일 미완료 항목, 전체보기 팝업
- 일정: 날짜별 읽기 전용 타임라인, 식당 목록, 예약자료, 일정별 준비 항목
- 지도: 날짜별 지도와 고정 장소 목록, 실패 시 외부 링크
- 준비: 출발 전 할 일, 공통 준비물, 일정별 준비 현황
- 더보기: 예약 전체 목록, 쇼핑, 긴급정보, 계정 등 유지 기능

## 5. 새 계획서와 데이터 반영 방식

### 5.1 계획서 필수 필드

| 대상 | 필수 정보 |
|---|---|
| 일정 | 변경되지 않는 schedule_key, 날짜, 종류, 제목, 시간 표기, 순서, 고정시간 여부 |
| 장소 | place_key, 정확한 지점명, 확인된 지도 URL, 확인일, Place ID는 확인된 경우만 |
| 식사 | 일정 키, 식당 키 목록, 표시 순서, 설명 |
| 이동 | 출발/도착, 탑승 위치, 교통수단, 계획 시간, 예약 필요 여부 |
| 준비물 | item_key, 일정 키 또는 공통 범위, 담당자, 반복 여부, 필수 여부 |
| 할 일 | item_key, PRE_TRIP/일정 범위, 담당자, 마감일, 중요도 |

자유로운 문장·정규식만으로 자료를 분류하지 말고 명시적 표 또는 구조화 블록을 사용한다. 현재 generate-seed.mjs는 행동 관련 단어로 준비물과 체크리스트를 나누므로 새 계획서에서는 이를 명시적으로 구분한다.

실제 예약번호·QR·좌석·개인 첨부는 공개 저장소 계획서에 넣지 않고 인증된 서비스 DB/Storage에 저장한다. 구체적인 일정·숙소·식당은 TRIP_PLAN.md의 2026-10-06-r3 버전을 따른다. 미확정 지점은 해당 계획서의 확인 목록에 남긴다.

### 5.2 기존 데이터 보존과 계획 갱신

현재 Seed는 ON CONFLICT DO NOTHING이므로 문서를 바꿔 다시 실행해도 같은 ID의 기존 일정은 수정되지 않는다. 또한 제목/위치 기반 ID를 바꾸면 예약 연결과 체크 상태가 끊길 수 있다.

1. 기존 DB와 첨부 연결 정보를 백업한다.
2. 안정적인 schedule_key/place_key/item_key와 기존 ID 매핑을 만든다.
3. 새 계획의 삽입·수정·제거 예정 목록과 연결된 사용자 데이터를 미리 출력한다.
4. 계획 소유 필드만 upsert한다. 예약 텍스트·첨부·사용자 추가 준비 항목·완료 상태는 덮어쓰지 않는다.
5. 사라지는 일정은 우선 보관 처리하고 연결된 예약/준비 항목의 재연결 또는 미분류 보관을 명시한다. cascade 삭제로 사용자 자료를 지우지 않는다.
6. 동일 계획을 다시 적용해도 중복이 생기지 않아야 한다.
7. 계획 버전과 적용 결과를 기록하고 롤백 절차를 둔다.

- Google API 장애 중에도 지도 링크·일정·예약자료를 사용할 수 있다.
- 실제 운영 키로 지도와 필요한 Places 기능을 별도 확인한다. fixture 테스트 통과를 운영 API 성공으로 간주하지 않는다.

- 각 일정에서 준비물/할 일을 적고 완료 상태를 바꿀 수 있다.
- 출발 전 할 일이 여행 중 매일 반복 항목으로 잘못 집계되지 않는다.
- 당일 전체보기는 다른 탭으로 이동하지 않고 모든 해당 항목과 완료 상태를 표시한다.
- 팝업을 닫으면 기존 위치로 돌아간다. 다른 계정과 동시 체크해도 상태가 일치한다.
- 새 계획 재적용 후에도 예약·첨부·사용자 항목·완료 상태가 보존된다.
- npm run lint, npm run typecheck, npm test, npm run build 및 영향받는 E2E 검증 결과를 기록한다. 이 제안서 작성 단계에서는 실행하지 않았다.

## 10. 디자인·UX 개편 명세 — Winter Companion

### 10.1 목표와 적용 범위

사용자가 선택한 방향은 ‘토스처럼 명료하고 편안한 UX + 겨울·크리스마스 감성’이다. 큰 제목, 충분한 여백, 일관된 컴포넌트, 분명한 주요 행동을 적용한다. senkyo만의 딥그린 색상과 작은 겨울 장식으로 정체성을 만든다.

로그인, 오늘, 일정, 일정 상세, 지도, 준비, 예약자료, 더보기와 모든 팝업·폼·오류 화면에 동일한 기준을 적용한다. 오늘 화면만 새 디자인으로 바꾸고 나머지를 기존 디자인으로 남겨두지 않는다.

우선 목표는 모바일에서 다음 일정·예약자료·준비물을 빠르게 확인하는 것이다. 실제 앱은 예약·준비 상태를 유지하는 기존 데이터 계층에 연결한다. 시안에 쓰인 예시 일정·체크 상태·버튼은 운영 데이터로 교체한다.

### 10.3 크리스마스·겨울 표현 규칙

- 홈 상단에 눈송이, 작은 별, 겨울 여행 배지 중 한두 요소를 사용한다.
- 로그인에는 짧은 겨울 여행 인사와 계절 일러스트를 넣을 수 있다.
- 이미지가 없는 식당·예약 카드에는 통일된 카테고리 아이콘을 사용한다.
- 배경 전체의 눈 내림, 반짝임 반복, 자동 재생 효과는 기본 적용하지 않는다.
- 초록색과 빨간색만으로 체크 완료/미완료를 표현하지 않고 체크 모양과 텍스트를 병행한다.
- 예약번호·QR·첨부 미리보기·시간 위에는 장식이나 반투명 레이어를 겹치지 않는다.
- 감성 문구는 홈 인사에 한정하고 오류·저장 결과·예약 안내는 정확하게 쓴다.

### 10.4 내비게이션과 반응형

하단 탭은 오늘 / 일정 / 지도 / 준비 / 더보기의 5개로 구성한다. 탭마다 아이콘과 한글 이름을 함께 표시한다. 활성 상태는 색상과 굵기로 구분하고 스크린리더 상태를 제공한다.

- 모바일: 하단 탭 고정, safe-area inset 반영, 본문 아래에 탭 높이만큼 여백 확보.
- 태블릿·데스크톱: 최대 너비 약 1080px의 중앙 레이아웃. 일정과 예약/준비 요약을 필요시 2열로 배치한다.
- 모바일 앱을 데스크톱에서 무조건 가로로 늘리지 않는다.
- 320px, 390px, 768px, 1280px에서 가로 넘침과 버튼 겹침을 확인한다.
- 탭 변경과 팝업 닫기 이후 선택 날짜 및 목록 위치를 유지한다.

### 10.5 화면별 UX

#### 로그인

서비스명 ‘둘이, 일본’, 짧은 여행 소개, 아이디·비밀번호 입력, 로그인 버튼에 집중한다. 겨울 장식은 상단에 배치한다. 회원가입이나 외부 초대를 추가하지 않는다. 입력 중 키보드가 열려도 로그인 버튼과 오류를 확인할 수 있어야 한다.

#### 오늘

표시 순서는 다음과 같다.

1. 현지 날짜, 여행 일차, 짧은 문구.
2. 현재/다음 일정 중 가장 필요한 항목 하나를 주요 카드로 표시.
3. 일정 종류에 맞는 주요 버튼: 이동은 ‘예약자료 보기’, 식사는 ‘식당 보기’, 관광은 ‘지도 보기’.
4. 미완료 준비물과 할 일을 구분해 요약하고 각 전체보기 버튼 제공.
5. 이후 일정의 간단한 목록과 오늘의 숙소.

주요 카드에는 시간, 제목, 출발·도착 또는 장소, 핵심 설명만 표시한다. 한 카드에 여러 개의 동일한 강조 버튼을 나열하지 않는다. 보조 행동은 텍스트 버튼으로 낮춘다.

여행 전에는 D-day와 여행 전 미완료 체크리스트를 먼저 보여주고 여행 일정은 ‘미리보기’로 표시한다. 여행 후에는 완료 안내와 전체 일정 접근을 제공한다. 모든 날짜를 오늘처럼 표현하거나 실제 날씨·예약 완료 여부를 임의로 생성하지 않는다.

#### 전체 일정

상단에 날짜 선택을 두고 시간순 타임라인을 제공한다. 이동·식사·숙소는 아이콘과 제목으로 구분한다. 선택한 날짜는 스크롤 이후에도 파악 가능하게 한다.

각 행에는 시간, 제목, 장소 요약, 필요한 자료가 있는지 표시한다. 내용이 긴 경우 상세로 열되 정확한 식당 지점명은 줄바꿈으로 확인 가능하게 한다. 일정 추가·수정·삭제·정렬 버튼은 표시하지 않는다.

#### 일정 상세

모바일은 바텀시트, 넓은 화면은 중앙 다이얼로그로 연다. 상세 안에서 시간·장소·설명은 읽기 전용이다.

- 식사: 계획서에 정한 여러 식당을 고정 순서로 표시. 각 식당의 지도 링크를 직접 제공.
- 이동: 예약 텍스트, 예약번호 복사, 첨부 보기·추가를 제공.
- 공통: 해당 일정의 준비물과 할 일을 바로 체크하고 항목을 작성·수정할 수 있다.
- 자료 추가 시 상세 위에 팝업을 계속 중첩하지 않는다. 같은 패널 안에서 작성 화면으로 전환하고 뒤로 돌아오게 한다.

#### 오늘의 준비물·체크리스트 팝업

‘준비물 전체’는 준비물 영역, ‘체크리스트 전체’는 할 일 영역이 선택된 동일 팝업을 연다. 팝업 제목에 선택 날짜를 명시한다.

공통 항목, 일정 시간순 항목을 묶고 담당자 및 관련 일정 이름을 표시한다. 전체/미완료 필터와 완료 수를 제공한다. 체크 후 항목을 즉시 재정렬해 손가락 아래에서 사라지게 하지 않는다. 현재 열려 있는 동안 순서를 유지하고 완료 모양만 바꾼다.

닫기 버튼·ESC·배경 클릭을 지원한다. 스와이프 닫기는 선택 사항이며 유일한 닫기 방식으로 사용하지 않는다. 내부 목록이 길면 본문 영역만 스크롤하고 제목·닫기는 접근 가능하게 유지한다.

#### 준비

‘여행 전’과 ‘여행 중’을 구분한다. 여행 전에는 마감일과 미완료 항목을, 여행 중에는 선택 날짜의 공통·일정별 준비를 보여준다. 담당자 구분은 이름을 표시하고 색만으로 구분하지 않는다. 완료 항목을 다시 열거나 되돌릴 수 있게 한다.

#### 지도

날짜별 장소를 지도와 함께 표시한다. 각 장소에서 외부 Google Maps를 직접 열 수 있게 한다. 내장 지도 로딩·실패·지점 미연결 상태를 각각 표현하고, 실패해도 아래 목록이 남아 있어야 한다. 장소 등록·검색·지점 연결은 운영 UI에 두지 않는다.

#### 예약자료

이동 일정에서 직접 진입하는 경로를 우선하고, 더보기의 예약 전체 목록도 유지한다. 파일 행에는 제목, 파일 종류, 크기, 보기 동작을 표시한다. 예약번호는 줄바꿈 또는 가로 넘침 없이 표시하며 복사 성공을 알린다. 업로드 중·실패·재시도·빈 자료 상태를 각각 설계한다.

### 10.6 공통 상호작용과 접근성

- 바텀시트: 포커스 진입·고정·복귀, 배경 스크롤 잠금, 스크린리더 이름, ESC 닫기.
- 애니메이션: 열림/닫힘 180~240ms 정도로 제한. prefers-reduced-motion이면 이동 애니메이션을 줄이거나 제거.
- 저장 버튼: 저장 중 중복 제출 차단, 결과 표시. 실패한 상태를 성공 체크로 남기지 않음.
- 체크 상태: 응답 전 미리 반영할 경우 실패 시 복구하고 오류 안내. 두 계정의 변경을 동기화.
- 로딩: 실제 카드 형태와 비슷한 스켈레톤 사용, 전체 화면을 불필요하게 빈 화면으로 만들지 않음.
- 빈 상태: ‘등록된 예약자료가 없어요’와 ‘자료 추가하기’처럼 다음 행동 제시.
- 오류: ‘예약자료를 저장하지 못했어요. 다시 시도해주세요’처럼 문제와 해결 행동 표시.
- 본문 대비 4.5:1 이상, 큰 글자와 주요 비텍스트 UI는 해당 접근성 기준에 맞춰 확인.
- 키보드 포커스 링, 200% 텍스트 확대, 긴 예약번호·일본어 지점명, 모바일 키보드 표시 상태 확인.
- 첨부 업로드 실패·삭제 오류는 잠깐 사라지는 알림만 사용하지 않고 해당 항목 가까이에 남겨둔다.

### 10.7 구현 구조 제안

기존 Next.js·React·Tailwind·lucide-react 구성 안에서 우선 구현한다. TDS 패키지 도입은 요구하지 않으며, 브랜드의 UI 원칙을 자체 컴포넌트로 구현한다. 디자인 라이브러리 전체 교체를 선행조건으로 삼지 않는다.

권장 공통 컴포넌트 예시:

- AppShell / BottomNavigation / PageHeader
- PrimaryButton / SecondaryButton / IconButton
- NextScheduleCard / ScheduleTimelineItem / MealPlaceRow
- PreparationRow / PreparationSummary
- ResponsiveSheet / AttachmentRow / ReservationPanel
- EmptyState / ErrorState / LoadingSkeleton

이름과 파일 경로는 저장소 구조에 맞게 조정한다. 기존 planner.tsx에서 화면·팝업·폼이 얽혀 있으면 관련 부분을 점진적으로 분리하고, 같은 DB 조회나 저장 함수를 화면마다 복제하지 않는다.

### 10.8 단계별 작업과 산출물

| 단계 | 작업 | 완료 산출물 |
|---|---|---|
| 1 | 현재 화면과 핵심 이용 흐름 기록, 명세 충돌 정리 | 현행 화면 캡처, 변경 대상 목록 |
| 2 | 색·글자·간격·버튼·팝업 공통화 | 공통 테마와 기본 컴포넌트 |
| 3 | 오늘 및 당일 전체보기 구현 | 실제 상태와 연결된 홈/팝업 |
| 4 | 읽기 전용 일정, 식당 목록, 이동 예약자료 구현 | 계획 조회부터 예약자료 확인까지 연결 |
| 5 | 준비·지도·로그인·더보기 및 오류 상태 적용 | 전체 화면의 디자인 일관성 |
| 6 | 데이터 보존·권한·반응형·접근성·상호작용 검증 | 검증 결과와 수정 전후 캡처 |

단계별로 동작하는 상태를 유지한다. 구조 변경과 데이터 migration은 앞 절의 보존 원칙을 따른다. 이미 최신 기능 개편이 적용돼 있다면 중복 구현하지 않고 현행 코드를 기준으로 남은 작업만 수행한다.

### 10.9 디자인·UX 완료 기준

1. 오늘 화면에서 다음 일정 시간과 장소를 즉시 식별할 수 있다.
2. 해당 이동의 예약자료는 오늘 카드에서 한 번의 주요 클릭으로 진입한다.
3. 준비물 전체보기가 다른 탭으로 이동하지 않고 열리며 체크 후 닫아도 날짜와 스크롤이 유지된다.
4. 식사 일정 안에서 각 고정 식당의 정확한 지점명과 지도 버튼을 찾을 수 있다.
5. 로그인부터 예약자료까지 색상·버튼·팝업·간격이 일관된다.
6. 320px 화면, 긴 문구, 첨부 오류, 여행 전/중/후, 데이터 없음 상태에서 화면이 깨지지 않는다.
7. 키보드·확대·모션 감소 설정으로 핵심 동작을 수행할 수 있다.
8. 새 디자인 적용 전후 같은 조건의 캡처를 비교한다. 바텀시트 열림과 오류 화면도 포함한다.
9. lint/typecheck/test/build와 관련 E2E 결과를 기록한다. 실제 사용성 검증을 하지 않았다면 ‘사용성 검증 완료’라고 쓰지 않는다.
